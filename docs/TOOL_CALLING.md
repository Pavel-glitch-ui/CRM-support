# Документация: Архитектура Tool Calling (Вызов инструментов ИИ)

## 1. Обзор нативного OpenAI Tool Calling

В ранних версиях проекта взаимодействие ИИ-агента с инструментом веб-поиска (`search_web`) строилось на базе спецификации **OpenAI Function / Tool Calling API**.

### Схема вызова:
```json
{
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "search_web",
        "description": "Поиск актуальной информации в интернете (бенчмарки рынка, конверсии, средние чеки)",
        "parameters": {
          "type": "object",
          "properties": {
            "query": {
              "type": "string",
              "description": "Поисковый запрос"
            }
          },
          "required": ["query"]
        }
      }
    }
  ],
  "tool_choice": "auto"
}
```

### Жизненный цикл двухфазного нативного диалога:
1. **Шаг 1 (Client ➔ LLM):** Отправка системного промпта, данных CRM и схемы `tools`.
2. **Шаг 2 (LLM ➔ Client):** Модель возвращает `choice.message.tool_calls` с аргументами: `{"query": "конверсия воронки b2b опт"}`.
3. **Шаг 3 (Client Execution):** Бот вызывает `searchWeb(query)` через DuckDuckGo.
4. **Шаг 4 (Client ➔ LLM):** Бот добавляет в массив сообщений:
   ```json
   {
     "role": "tool",
     "tool_call_id": "call_12345",
     "name": "search_web",
     "content": "[Результаты поиска...]"
   }
   ```
5. **Шаг 5 (LLM ➔ Client):** Модель формирует финальный текст бизнес-аудита.

## 2. Причины отказа от нативного Tool Calling на бесплатных моделях OpenRouter

При работе с бесплатными эндпоинтами OpenRouter (`:free`) нативный Tool Calling приводил к следующим критическим проблемам:

1. **Несовместимость схемы сообщений (`role: 'tool'`)**:
   Многие открытые модели (OpenChat, Nemotron, Mistral, GLM) на бэкендах OpenRouter не поддерживают формат `role: 'tool'` и возвращали ошибку 400 или пустой ответ на Шаге 4.
2. **Маршрутизация на разные бэкенды**:
   При использовании роутеров вроде `openrouter/free` Шаг 1 обрабатывался одним сервером (поддерживающим `tool_calls`), а Шаг 4 — другим (который не знал о предыдущем вызове и сбрасывал сессию).
3. **Сырые псевдо-XML теги**:
   Некоторые модели вместо JSON структуры отдавали текст `<toolcall><function=searchweb>...</toolcall>`, который не перехватывался библиотекой OpenAI SDK.
4. **Двойная задержка**:
   Необходимость делать 2–3 последовательных сетевых вызова к LLM увеличивала время ответа до 20–40 секунд.

## 3. Новая архитектура: Pre-Search RAG (Context Injection)

Вместо ожидания, пока модель запросит инструмент, бот использует подход **Pre-Search Enrichment (RAG)**:

1. **Мгновенный пре-поиск (0.3–0.5 сек)**: При запуске аудита по указанной нише (`niche`) бот сразу запрашивает отраслевые бенчмарки в DuckDuckGo.
2. **Единый обогащенный контекст**: Данные из CRM и свежие результаты поиска объединяются в единый структурированный промпт.
3. **Один быстрый вызов LLM**: Модель получает полный набор информации сразу и за **один вызов** генерирует цельный аудит без риска сбоев API.

## 4. Как вернуть нативный Tool Calling (при переходе на платный OpenAI / Anthropic)

Если в будущем проект перейдет на платный API OpenAI (`gpt-4o`, `gpt-4o-mini`) или Anthropic Claude:

1. В `src/config.ts` укажите модель `gpt-4o-mini` и ключ `OPENAI_API_KEY`.
2. В `src/ai/agent.ts` передайте `tools: [searchToolDefinition]` в `callParams`.
3. Обрабатывайте `responseMessage.tool_calls` стандартным циклом OpenAI SDK.
